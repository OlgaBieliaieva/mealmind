# MealMind API

MealMind API — серверна межа застосунку, яка відповідає за автентифікацію,
авторизацію, збереження даних і виконання бізнес-сценаріїв.

## Операційні endpoints

- `GET /health` перевіряє, чи працює процес API.
- `GET /ready` перевіряє доступність необхідної інфраструктури.

Endpoint `/health` не звертається до бази даних. Endpoint `/ready` виконує
мінімальну перевірку підключення до PostgreSQL.

## Політика HTTP-запитів

- Розмір JSON body обмежений до 256 КіБ.
- API-платформа не приймає multipart uploads.
- Медіафайли не можна передавати як Base64-значення у JSON.
- Вхідний request ID приймається лише тоді, коли відповідає визначеному
  безпечному формату.
- HTTP-запити та неактивні з’єднання мають обмежений час очікування.

## Rate limiting

Прикладні маршрути під `/api/v1` мають базовий IP-based rate limit:

- 120 запитів;
- window 60 секунд;
- standard `RateLimit` headers;
- відповідь `429 RATE_LIMIT_EXCEEDED` після вичерпання quota.

Операційні endpoints `/health` і `/ready` не входять до прикладної quota,
щоб platform health checks не блокувалися користувацьким трафіком.

Поточний in-memory store відповідає одному Render Starter instance. Під час
масштабування API на кілька instances потрібно перейти на спільний
Redis-compatible store, щоб усі процеси використовували один лічильник.

## Політика логування

Логи зберігаються у форматі структурованих JSON-записів.

Лог HTTP-запиту може містити:

- request ID;
- HTTP-метод;
- шлях endpoint без значень query parameters;
- HTTP-статус відповіді;
- тривалість оброблення запиту;
- внутрішній ідентифікатор автентифікованого користувача.

До логів заборонено записувати:

- request body;
- значення query parameters;
- заголовки авторизації;
- cookies;
- паролі й access tokens;
- реквізити підключення до бази даних;
- ключі Supabase;
- персональні дані про здоров’я;
- назви спожитих продуктів і страв;
- значення нутрієнтів.

## Відстеження помилок

Структуровані runtime-логи формуються за допомогою Pino та виводяться у
стандартний потік виведення.

Централізоване відстеження production exceptions за допомогою Sentry
додається окремо. Sentry не замінює операційні логи, health checks
або readiness checks.

Sentry events повинні використовувати request ID для кореляції та не
містити request body, authorization headers, cookies, ключі доступу,
персональні дані про здоров’я або інші чутливі відомості.

## CORS

Дозволені браузерні origins визначаються змінною середовища
`CORS_ALLOWED_ORIGINS`.

CORS не є механізмом авторизації. Кожен захищений endpoint повинен окремо
застосовувати перевірену автентифікацію та відповідну доменну авторизацію.

Запити без заголовка `Origin`, зокрема server-to-server запити та перевірки
стану сервісу, можуть оброблятися API.

## Завершення роботи

API обробляє сигнали `SIGTERM` і `SIGINT`.

Під час контрольованого завершення API:

1. припиняє приймати нові з’єднання;
2. очікує завершення активних запитів;
3. після завершення визначеного часу примусово закриває залишкові з’єднання;
4. від’єднує Prisma Client від бази даних;
5. завершує процес без втрати контрольованих операцій.

Повторний сигнал завершення не запускає паралельну процедуру shutdown.
