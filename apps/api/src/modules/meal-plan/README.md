# Модуль тижневого плану харчування

Модуль `meal-plan` володіє канонічним сімейним планом, його позиціями,
персональними порціями та агрегованим read model. Активна сім’я завжди
визначається на сервері з authenticated identity; `familyId`, роль і право
керувати чужим профілем клієнт не передає.

## HTTP-контракти

- `GET /api/v1/meal-plans/week?date=YYYY-MM-DD&days=...` — сім днів
  канонічного тижня та нутрієнтні агрегати лише для вибраних `days`;
- `GET /api/v1/meal-plans/planning-context?date=...` — повний available week,
  учасники, їхні дозволені типи прийомів їжі та server-derived `canPlan`;
- `POST /api/v1/meal-plans/entries/batch?date=...` — атомарне створення або
  контрольоване об’єднання позицій;
- `PATCH /api/v1/meal-plans/entries/:entryId` — переміщення позиції власником;
- `PATCH|DELETE /api/v1/meal-plans/entries/:entryId/participants/:memberId` —
  зміна порції або вилучення учасника;
- `PATCH /api/v1/meal-plans/entries/:entryId/prepared` — позначення готовності
  позиції без створення факту споживання;
- `DELETE /api/v1/meal-plans/entries/:entryId` — видалення всієї позиції
  власником сім’ї.

Усі маршрути authenticated і rate-limited. Помилки мають стабільні коди
`MEAL_PLAN_VALIDATION_FAILED`, `MEAL_PLAN_ACCESS_DENIED`,
`MEAL_ENTRY_NOT_FOUND`, `MEAL_PLAN_CONFLICT` та
`MEAL_PLAN_IDEMPOTENCY_CONFLICT`.

## Модель і транзакції

Один `MealEntry` представляє одну їжу в комбінації дата + прийом їжі й може
мати кілька `MealEntryParticipant`. Це не окремий запис на кожного члена
родини. Порція в mutation-контракті передається як `quantityGrams`; backend
зберігає її у базовій активній одиниці маси. Неявне перетворення ml або штук
у грами не виконується.

Batch є повністю атомарним і обмежений 50 позиціями. Усі учасники, дати,
налаштування прийомів їжі та видимість продуктів/рецептів повторно
перевіряються в serializable transaction. `requestId` і fingerprint payload
зберігаються в `MealPlanMutationRequest`: повтор того самого запиту повертає
попередній результат, а повторне використання ключа з іншими даними дає 409.

`MealEntry.revision` використовується для optimistic concurrency. Update і
delete приймають `expectedRevision`; stale команда не перезаписує новіші дані.
OWNER може планувати для всіх активних профілів. MEMBER може змінювати лише
власну порцію і не може переміщувати або видаляти shared entry.

Read model для MEMBER повертає тільки його профіль, його порцію та персональні
нутрієнтні агрегати. Плани й порції інших членів родини не потрапляють у
відповідь API.

## Межа плану та споживання

Meal plan не має статусів `completed` або `skipped`. `PENDING`, `CONFIRMED`,
`CHANGED` і `SKIPPED` належать майбутньому read model щоденника або окремій
resolution, а не `MealEntry`. Поле read model називається `planned`, а сигнали
використовують нейтральні формулювання «заплановано менше/більше за ціль».

`preparedAt` і `preparedByUserId` фіксують лише готовність страви в межах
планування. Цей стан не означає споживання, не впливає на нутрієнтні агрегати
та не створює запис у щоденнику. OWNER може змінити його для сімейної позиції,
MEMBER — тільки якщо є учасником цієї позиції.

Для продукту нутрієнти масштабуються з `valuePer100g`. Для рецепта
використовується частка `quantityInGrams / yieldWeightG`. Добові targets
визначаються окремо для кожної вибраної дати з урахуванням періоду дії
версійованого `NutrientTargetSet`, а для загального періоду підсумовуються.
Target projection зберігає `minimumValue`, `targetValue` і `maximumValue`:
точні, мінімальні, максимальні та діапазонні цілі не зводяться до одного
значення. Для багатоденного періоду межі конкретного нутрієнта підсумовуються
лише тоді, коли його ціль наявна для кожної вибраної дати.
Якщо активний набір цілей відсутній хоча б для одного вибраного дня, API не
видає хибну оцінку відповідності за неповний період. Відсутні значення не
підмінюються нулем.

Режим за прийомами їжі повертає сумарні нутрієнти всіх вибраних порцій. Цей
сімейний підсумок не порівнюється з персональними цілями. Режим за членами
родини рахує показники окремо для кожного профілю та формує нейтральні сигнали
лише за наявності цільових значень. Відсутність цілей є окремим станом UI з
пропозицією доповнити профіль, а не станом «у межах балансу». Якщо для
запланованих позицій відсутня частина базових нутрієнтів, значення
відображаються, але висновок про відповідність цілям не формується.
У деталізації member view клієнт показує формат `заплановано / ціль` або
`заплановано / мін–макс` для енергії та макронутрієнтів.

## Клієнтські сценарії

Швидкий сценарій дозволяє обрати профіль, прийом їжі й кілька продуктів або
рецептів у пошуку. Advanced member-first workspace відкриває повний тиждень,
дає незалежно вибрати дні, прийоми та порцію для кожного доступного профілю,
показує review і надсилає один атомарний batch.

Чернетка advanced flow зберігає тільки IDs і кількості в `sessionStorage` під
ключем `familyId + weekStart + kind + foodId`. Вона не переноситься між
сім’ями/тижнями, очищується після успішного submit і відновлюється після
refresh. URL зберігає shareable navigation context (`date`, `returnTo`), а не
довірені authorization-дані.
